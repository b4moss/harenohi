# データソースと更新フロー

PO 方針: 過去は政府 CSV、来年は発表時期に Actions で取得、未来の未確定は演算。

## 政府 CSV

- 内閣府等が公開する「国民の祝日」CSV（いわゆる `syukujitsu.csv`）を正の過去・確定データとする
- 文字コードは Shift_JIS 等の可能性あり。パース時に変換する（参照: life の `parse-jp-holiday-csv.mjs`）
- 1 行: 日付と名称。日付を `YYYY-MM-DD` に正規化し、年ごとの JSON オーバーライドへ落とす

## リポジトリ内の置き場（案）

```
src/
  data/jp-holiday/
    source/          # 取得した CSV（必要なら git 管理）
    override/        # 年ごと JSON（例: 2024.json）
scripts/
  fetch-jp-holiday-csv.*   # 取得（Actions から呼ぶ）
  parse-jp-holiday-csv.*   # CSV → override JSON
```

パスは実装時に調整してよい。意味の分離（source / override / scripts）は維持する。

## オーバーライド JSON

```json
[
  { "title": "元日", "date": "2026-01-01" },
  { "title": "成人の日", "date": "2026-01-12" }
]
```

- ファイル名は西暦でも、各要素の `date` には必ず西暦を含める
- その年の全日分を列挙する（部分上書きではない）。ある年にファイルがあれば演算を使わない

## 来年分の更新（Actions）

1. 政府が翌年分を公表した時期に、ワークフローを手動またはスケジュールで実行
2. CSV を取得
3. パースして `override/` に該当年を生成または更新
4. PR を作成し、人が確認してからマージする（U-09 / D-18 決定）

CI 上の取得失敗はワークフローを失敗させ、黙って古いデータのままリリースしない。

## 過去分の初期投入

- 現行祝日法以降〜入手可能な最新確定年までを、一度 CSV から生成してコミットする
- life リポに既にある override / source があれば、ライセンスと出自を確認のうえ移植してよい

## ランタイムとの関係

- 公開 API はディスクや HTTP にアクセスしない
- オーバーライドはビルド成果物またはバンドル内データとして同梱する
- 「最新 CSV を実行時に読む」は v1 スコープ外

## テスト観点（データ）

- パース: 代表行・空行・不正行の扱い
- 生成 JSON が型（title/date）を満たすこと
- 既知年（例: 2024, 2025）で政府公開と一致すること
- オーバーライドがある年に演算パスが呼ばれないこと（単体でスタブまたは分岐カバレッジ）
